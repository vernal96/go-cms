# Оптимизация чтения — 0.3.0

Выпуск обновляет зависимость starter до `github.com/vernal96/go-cms-kernel v0.3.0`.
HTTP-ответы, правила доступа и схема БД не менялись.

## Изменения

- `security.Authorizer.Allowed(ctx, actor, codes)` возвращает разрешённые коды
  в порядке входного списка, без дублей. Одиночный `Check` использует ту же
  политику. Неизвестные коды, ошибки аутентификации и хранилища остаются ошибками.
- PostgreSQL читает состояние пользователя и запрошенные групповые/гостевые
  разрешения одним SQL-запросом. Правила их применения остаются в access-сервисе.
  Результаты не кешируются между операциями; отзыв прав виден следующему вызову.
- Сессия админки, dashboard и наборы возможностей используют пакетную проверку.
  Проверки доступа к конкретному сайту сохраняются отдельно.
- Страницы LibraryItem получают версии без отдельного запроса. Версии
  присоединяются после `LIMIT`; внешняя сортировка сохраняет порядок страницы,
  включая пользовательские поля, отсутствующие значения и курсоры.
- Dashboard выполняет до трёх независимых веток: «сайты → ресурсы», пользователи,
  группы. Ошибка отменяет остальные операции; частичный ответ не возвращается.

## Изменения контрактов расширения

- Собственные реализации `security.Authorizer` должны реализовать `Allowed`.
  Запрещённые коды отсутствуют в результате; пустой список не требует I/O.
- Access-репозиторий реализует `Authorization` вместо `GroupAllowed` и
  `GuestAllowed`: состояние субъекта и разрешения возвращаются вместе.
  Метод `Subject` сохраняется для проверки привилегий и доступа к сайтам.
- Статистические репозитории должны поддерживать конкурентные вызовы и отмену
  `context.Context`.
- Совместимые обходные пути не добавлены. Отдельный frontend-admin не менялся
  и сохраняет прежнюю версию.

## Проверенные результаты

На изолированном PostgreSQL 18 с `pg_stat_statements`:

| Операция | До | После |
|---|---:|---:|
| Перечисление N разрешений пользователя с группами | 2N SQL | 1 SQL |
| Обычная непустая страница LibraryItem | 4 SQL | 3 SQL |
| Страница из двух веток сортировки по пользовательскому полю | 5 SQL | 4 SQL |
| Пустая обычная страница | 1 SQL | 1 SQL |

HTTP-тест сессии выполняет три SQL-запроса: проверка входа в админку, чтение
профиля и пакетная авторизация. Actor задаётся тестом; JWT middleware в этот
счётчик не входит.

Локальный SQL-замер: 20 000 LibraryItem, у половины заполнено поле `rank`,
страница из 50 элементов плюс lookahead; `pgbench -M prepared -c 4 -j 4 -t 200`,
три серии с чередованием вариантов. Медианы среднего времени операции по сериям:

| Выборка | До, мс | После, мс |
|---|---:|---:|
| По ID | 1,538 | 1,424 |
| Заполненное поле | 1,704 | 1,516 |
| Отсутствующее поле | 6,753 | 6,833 |

Для отсутствующего поля существенного ускорения не наблюдается, но устранён
один запрос. План сохраняет top-N сортировку; версии читаются только для
отобранной страницы. Эти измерения не являются production SLA или HTTP latency.

В kernel прошли полный набор Go-тестов, PostgreSQL-интеграции, проверки `-race`
изменённых подсистем, `go vet`, `go build`, `go mod tidy -diff`. Проверены отзыв
прав, блокировка, guest/system/superuser, несколько групп, изоляция сайтов,
версии и курсоры LibraryItem, параллельный запуск и отмена веток dashboard.
Отдельные kernel-интеграции Kafka/S3/Redis в этом прогоне не запускались.

  `sum.golang.org`, при `GOWORK=off`, без `replace`.

- Прошёл `make test-deployment`: чистая копия исходников, отдельный Compose
  project, новые PostgreSQL/Kafka/filesystem volumes и Redis, сборка из
  опубликованной Go-зависимости.

  ресурсов, public/private файлы, отказы в неавторизованном доступе, видимость
  ошибки запуска в Docker logs и сохранность данных при пересоздании контейнеров.
- Временные контейнеры и volumes удалены автоматически после успешной проверки.
- CI kernel успешно выполнился для release-коммита `8f2fc18` и тега `v0.3.0`.
