# Release protocol — kernel, admin, starter

Релиз публикует только PM после принятого результата, синхронизации версий, документации, локальных/CI проверок и UI QA. Нельзя создавать релиз, если критический сценарий не проверен или сборка упала. Для одного набора задач составляй один согласованный release plan.

## Идентификация версий

На каждом запуске сверяй фактические git tags и последнюю версию из репозитория, не ориентируйся только на README/CHANGELOG: они могут отставать. Работай только на main.
- go-cms-kernel: семантические git-теги vX.Y.Z, версия Go module.
- go-cms-admin: version в package.json и package-lock.json + семантический git-тег; не делай npm publish без отдельного требования.
- go-cms: файл VERSION, CHANGELOG.md и семантический git-тег; Go dependency на kernel закреплена в backend/go.mod.

Выпускай релизы затронутых компонентов после каждого принятого цикла. Если заказчик требует синхронный релиз всех трёх — выпусти все три, но не добавляй выдуманных изменений и объясни, какие компоненты не меняли код. При отсутствии изменений/незакрытой приёмке не создавай пустой release/tag автоматически.

## Порядок

1. Зафиксировать перечень изменённых репозиториев, взаимозависимости и версионные изменения. Убедиться, что рабочие деревья предсказуемы, нет сторонних незафиксированных изменений.
2. go-cms-kernel при изменениях: обновить CHANGELOG, go test ./..., go vet ./..., go build ./..., go mod tidy -diff. После успешного CI создать новый уникальный SemVer tag на main и GitHub Release с содержательными notes. Не изменять существующие теги, не применять force.
3. go-cms-admin при изменениях: обновить package.json и lock синхронно; CHANGELOG, npm ci, npm test, npm run typecheck, npm run build, npm pack. После успешного CI новый tag и GitHub Release; npm registry — отдельно.
4. go-cms: если изменился kernel, обновить backend/go.mod и go.sum на выпущенную версию, перепроверить сборку и тесты; обновить README/VERSION/CHANGELOG по факту. Запустить make check и при доступном Docker make test-deployment, smoke. Проверить интеграцию с новой admin сборкой.
5. Только после успешных проверок/QA создать starter tag и GitHub Release.
6. Отчитаться о каждой ссылке на GitHub Release/tag, SHA, версиях зависимостей, успешных проверках, пропусках и возможных ограничениях.

## Версионирование и безопасное поведение

- Выбор PATCH/MINOR/MAJOR по фактическому характеру изменений и SemVer; до 1.0 Breaking changes обычно требуют как минимум осознанного MINOR bump. Не переписывай существующие теги.
- При падении CI, ошибке публикации или несовместимости — STOP_RELEASE. Не называй частичный выпуск завершённым и не пытайся скрыть расхождение версий.
- Не публикуй релизы из незавершённого задания, не коммить секреты, не изменяй чужие данные и не делай сброс базы ради прохождения тестов.
- Если окружение или права не позволяют git push / GitHub Release, подготовь готовый release plan и явно сообщи BLOCKED вместо заявления об опубликованном релизе.
